# Конституция проекта Workout Counter React

Этот документ фиксирует неизменяемые принципы проекта и правила принятия изменений.

## 1. Цель продукта

Проект помогает считать повторения упражнений по видео с веб-камеры в реальном времени, с акцентом на:

- предсказуемое поведение UI;
- прозрачность состояния тренировки;
- простоту расширения новыми упражнениями;
- стабильность работы в браузере.

## 2. Принципы разработки

1. **Понятность важнее магии**
   - Логика должна быть читаемой и локальной.
   - Любая сложная ветка поведения должна быть объяснима по коду и документации.

2. **Состояние сессии — источник истины**
   - Поведение `Старт`, `Пауза`, `Сброс`, `Стоп камера` должно быть однозначным.
   - Изменения, влияющие на жизненный цикл сессии, обязательно документируются.

3. **Расширяемость через контракты**
   - Новые упражнения добавляются через `ExerciseDetector`, без ломки существующих API.
   - Реестр упражнений остаётся динамическим и предсказуемым.

4. **Документация — часть поставки**
   - Любая заметная правка поведения продукта сопровождается обновлением релевантных docs.

## 3. Качество и верификация

- Перед завершением задачи выполняются проверки:
  - `npm run lint`
  - `npm run test` (когда правка затрагивает логику детекторов/сессии)
- Новые проверки не должны ухудшать UX (ложные срабатывания, сбросы прогресса, регресс голосовых команд).

## 4. Правила изменения продукта

Для задач, меняющих поведение продукта, соблюдается цикл планирования и реализации:

1. Сначала создаются артефакты плана и чеклиста:
   - `features/<name>/` для фич,
   - `fixes/<name>/` для исправлений.
2. Затем вносятся кодовые и документационные изменения по чеклисту.
3. После завершения каталог задачи переносится в архив:
   - `features/_archive/<name>/` или `fixes/_archive/<name>/`.

Цикл оформляется тремя отдельными коммитами:

1. План.
2. Реализация.
3. Архивирование.

Переход между этапами выполняется только после явного подтверждения.

## 5. Архитектурные инварианты

- Основная бизнес-логика сессии размещается в `src/app/useWorkoutSession.ts`.
- UI-команды и голосовые команды должны использовать единые действия сессии (`start`, `pause`, `reset`, `shutdown`).
- Детекторы упражнений изолированы, независимы друг от друга и работают через общий интерфейс.
- Рендер отделён от вычисления состояния.

Подробная техническая схема: [docs/architecture.md](docs/architecture.md).

## 6. Правило обратной совместимости UX

Изменения, которые влияют на пользовательские сценарии (кнопки, голос, отдых, статус-бар), не должны:

- неожиданно сбрасывать прогресс;
- менять смысл существующих команд без явного описания в документации;
- ухудшать доступность базового сценария "выбрал упражнение -> старт -> пауза/продолжение -> стоп".

Если смысл поведения изменён намеренно, это фиксируется в:

- `README.md`,
- профильных docs (`docs/voice-commands.md`, `docs/architecture.md`).

## 7. Приоритет при конфликте правил

1. Эта Конституция.
2. `README.md` и профильные docs проекта.
3. Локальные правила каталогов (`features/README.md`, `fixes/README.md`).
4. Временные договорённости в рамках конкретной задачи.
