# План фичи: управление пользователями и роли доступа

Ссылка на правила процесса: `README.md`, `specs/features/README.md`.

## Контекст

Сейчас аутентификация поддерживает только логин/пароль и возвращает `id/login` пользователя.
Ролевой модели нет, поэтому все авторизованные пользователи имеют одинаковый доступ, включая страницу `/admin`.

В проекте уже есть backend на Express + SQLite (`server/src/index.ts`, `server/src/db.ts`) и frontend-модули страниц/роутинга (`src/pages`, `src/routes`, `src/App`), что позволяет добавить роли и модуль управления пользователями без смены текущего стека.

## Цели

- Добавить роли `superadmin`, `admin`, `user` в модель пользователей.
- Ограничить доступ к страницам по ролям:
  - `superadmin` — все страницы.
  - `admin` — все страницы кроме управления пользователями.
  - `user` — только `Home` и `ExerciseHistory`.
- Добавить страницу/модуль управления пользователями для `superadmin`.
- Создать при инициализации БД пользователей `admin` и `superadmin` с паролем `12345678`.
- Включить признак обязательной смены пароля после первого входа для seeded-админов.

## Нецели

- Не вводить сложную ACL-модель на уровне отдельных действий внутри одной страницы.
- Не менять пользовательские роли массово через миграционный скрипт вне текущей БД приложения.
- Не менять формат токена за пределами нужного для ролей и флага смены пароля.

## Технический подход

1. **Слой БД и auth backend**
   - Расширить таблицу `users` полями `role` и `must_change_password`.
   - Добавить backfill для существующих пользователей: роль `user`, `must_change_password = 0`.
   - Добавить seed `admin` и `superadmin` с паролем `12345678` и `must_change_password = 1`.
   - Добавить операции списка пользователей и обновления роли/пароля.

2. **API и авторизация**
   - Расширить `AuthUser`-ответ (`/api/me`, `/api/login`, `/api/register`) полями роли и флага смены пароля.
   - Добавить серверные проверки ролей для админ-эндпоинтов.
   - Добавить endpoint управления пользователями (`/api/admin/users`) с доступом только для `superadmin`.
   - Добавить endpoint смены пароля текущего пользователя (сброс `must_change_password`).

3. **Frontend auth + роутинг**
   - Расширить `auth`-типизацию и селекторы полями роли и `mustChangePassword`.
   - Добавить role-based guard на маршруты по `RouteObject.handle`.
   - Ограничить навигацию по ролям.
   - Добавить обязательный редирект на страницу смены пароля при `mustChangePassword = true`.

4. **Модуль управления пользователями**
   - Создать `UserManagementModule` в `src/modules` по правилам модулей.
   - Реализовать таблицу пользователей и смену роли (кроме self-demotion для текущего superadmin).
   - Добавить страницу и маршрут, доступный только `superadmin`.

## Этапы

1. Расширить backend-модель пользователей и auth-ответ.
2. Добавить API для списка/изменения пользователей и смены пароля.
3. Внедрить role-based guards и ограничения меню на frontend.
4. Реализовать модуль/страницу управления пользователями.
5. Обновить документацию и прогнать проверки (`lint`, `test`).

## Критерии готовности

- Все текущие пользователи в БД имеют роль `user`.
- В БД присутствуют `admin` и `superadmin` с паролем `12345678` и обязательной сменой пароля после логина.
- `superadmin` имеет доступ ко всем страницам.
- `admin` не имеет доступа к странице управления пользователями.
- `user` имеет доступ только к `Home` и `ExerciseHistory`.
- Страница управления пользователями доступна и функциональна для `superadmin`.
- `npm run lint` и `npm run test` проходят успешно.
