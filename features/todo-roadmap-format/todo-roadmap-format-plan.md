# План: преобразование todo в читаемый формат

## 1. Контекст и проблема

- Сейчас [todo.md](../../todo.md) — плоский список с неоднородной нумерацией (`0`, `0.1`, `1`–`6`), без группировки по темам и без кратких пояснений к пунктам.
- На GitHub и в редакторе такой файл тяжело сканировать: неочевидны связь подпункта `0.1` с блоком «Управление голосом» и приоритет направлений.
- [README.md](../../README.md) уже указывает на `todo.md` как на бэклог идей — точка входа должна оставаться предсказуемой (короткая ссылка, понятное имя файла).

**Цель:** сохранить `todo.md` как единственный публичный бэклог идей, но оформить его так, чтобы на первый взгляд были видны темы, состав работ и смысл каждого пункта.

## 2. Целевая аудитория

| Аудитория | Что нужно |
|-----------|-----------|
| Автор / команда | быстро находить направление и подзадачи без расшифровки номеров |
| Новый участник | понимать масштаб идеи по одному–двум предложениям |
| Читатель README | по ссылке попадать в аккуратную дорожную карту, а не в «сырой» список |

## 3. Принципы

- **Один источник правды по идеям:** не дублировать полный бэклог в README; при необходимости в README остаётся одна фраза-ссылка (как сейчас).
- **Читаемость в markdown:** заголовки, списки, при необходимости таблица «направление → кратко о чём»; без зависимости от внешних генераторов сайтов (опционально позже).
- **Сохранение смысла:** все текущие пункты из `todo.md` должны найти отражение в новой структуре (ничего не терять без явного решения).
- **Единый стиль с проектом:** русский язык, тон как в [README.md](../../README.md) и в [features/documentation/documentation-update-plan.md](../documentation/documentation-update-plan.md).

## 4. Целевой вид (концепция)

Рекомендуемая структура файла `todo.md`:

1. **Заголовок и вводный абзац** (1–3 строки): что это за документ и как им пользоваться.
2. **Группы по темам** — логические разделы второго уровня (`##`), например:
   - голос и сценарий тренировки;
   - расширяемость упражнений;
   - аккаунт и данные;
   - планирование и аналитика;
   - новые типы нагрузки / детекторы.
3. **Внутри раздела** — нумерованный или маркированный список; у каждого пункта при желании:
   - **краткое описание** (зачем / что даст пользователю);
   - при необходимости подпункты без «магической» нумерации вроде `0.1` — лучше вложенный список под родительским пунктом.
4. **Опционально:** в начале документа компактная **таблица обзора** (направление | статус идеи | комментарий), если таблица не раздувает файл; иначе ограничиться разделами.

Итог должен хорошо рендериться на GitHub (заголовки, списки, таблицы).

## 5. Этапы работ

### Этап A. Инвентаризация

- Зафиксировать полный перечень текущих строк из `todo.md` и сопоставить каждой будущей группе и пункту.
- Отметить зависимости (например, «история упражнений» логично после «авторизации») — в тексте как примечание, без обязательной колонки Gantt.

### Этап B. Проектирование структуры

- Утвердить набор разделов `##` и порядок (например: от ближнего к продукту к более крупным фичам).
- Решить, нужна ли таблица-обзор в начале или достаточно только разделов.

### Этап C. Перенос содержимого

- Переписать `todo.md` в новом формате, сохранив все идеи из текущей версии.
- Проверить отображение в превью markdown (GitHub или IDE).

### Этап D. Согласование с точками входа

- Убедиться, что формулировка ссылки в README по-прежнему верна (файл остаётся `todo.md` в корне).
- При необходимости одной строкой обновить упоминания в других документах (если где-то описывался «старый» вид списка).

## 6. Критерии готовности

- В `todo.md` нет потерянных идей относительно состояния на момент начала работ.
- Документ имеет заголовки разделов; подпункт `0.1` оформлен как явная подзадача родительского пункта, а не отдельный «нулевой» уровень.
- Превью на GitHub выглядит аккуратно: непрерывные списки, корректные таблицы (если используются), нет «висячих» однострочников без контекста.
- README не противоречит новому виду бэклога (при необходимости — минимальная правка одной фразы).
