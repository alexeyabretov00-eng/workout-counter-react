# План: глобальная шина событий (singleton)

Связанный чеклист: [global-event-bus-implementation-tasks.md](./global-event-bus-implementation-tasks.md).

## 1. Контекст и цель

- Доменные модули (`src/modules/…`) должны оставаться пригодными для разных сценариев использования и **не зависеть от роутинга**.
- Навигацию и склейку модулей оставляем на **страницах** и при необходимости на layout-корне; модули выражают намерения через **события**.
- **Цель:** ввести **один глобальный экземпляр** шины (класс + singleton), **единый канонический список имён событий** (логические имена типов); подписчики на границе приложения вызывают навигацию и оркестрацию, эмиттеры — в модулях.

## 2. Границы фичи

**Входит:**

- Шина на основе **`window.dispatchEvent` / `window.addEventListener`** и браузерного **`CustomEvent`**: единый строковый префикс для имён DOM-событий (например `app:`), передача данных через **`detail`**.
- Публичный API без React: тип обработчика **`EventHandler = (detail: unknown) => void`**, методы **`emit(type, detail?)`** и **`on(type, handler)`**, где **`on` возвращает функцию отписки**.
- Защита для среды **без `window`** (SSR / предрендер): в **`emit`** и **`on`** при `typeof window === 'undefined'` не обращаться к DOM; **`emit`** — no-op, **`on`** — возвращать пустую функцию отписки.
- **`export const eventBus = new EventBus()`** — один экземпляр на приложение.
- **Единый список логических имён** `type` (без префикса в публичном API): централизованные константы в одном модуле; в коде **эмит и подписка** используют только их (не произвольные строки).
- По возможности типизация payload поверх `unknown` (например `EventMap` для известных типов) — согласованно со списком имён.
- Размещение: **`src/utils/eventBus/`**, баррель **`src/utils/eventBus/index.ts`** (без `export *`).

**Не входит:**

- **Хуки** в составе шины (`useEventBus`, `useEventBusSubscription` и т.п.) — подписка в компонентах только вручную: **`useEffect` + возвращённая из `on` функция отписки**.
- Перевод всего приложения на события за один раз — допускается поэтапное внедрение с пилотным экраном.
- Отдельный UI для отладки событий (опционально позже).

## 3. Архитектура

### 3.1. Ориентир реализации (контракт)

Логика шины соответствует следующему контракту (экспорт и имена могут быть слегка расширены типами, но поведение сохраняется):

```ts
type EventHandler = (detail: unknown) => void;

const EVENT_PREFIX = 'app:';

class EventBus {
  emit(type: string, detail?: unknown): void {
    if (typeof window === 'undefined') {
      return;
    }

    const event = new CustomEvent(`${EVENT_PREFIX}${type}`, { detail });
    window.dispatchEvent(event);
  }

  on(type: string, handler: EventHandler): () => void {
    if (typeof window === 'undefined') {
      return () => {};
    }

    const eventType = `${EVENT_PREFIX}${type}`;
    const wrappedHandler = (event: Event): void => {
      handler((event as CustomEvent).detail);
    };

    window.addEventListener(eventType, wrappedHandler as EventListener);

    return () => {
      window.removeEventListener(eventType, wrappedHandler as EventListener);
    };
  }
}

export const eventBus = new EventBus();
```

Именно **логический** `type` (без префикса) входит в единый список констант; на DOM навешивается **`${EVENT_PREFIX}${type}`**.

### 3.2. Singleton

- Один экспорт **`eventBus`**; отдельные инстансы под страницы **не** вводятся.

### 3.3. Единый список имён событий

- Файл вроде **`events.ts`**: константы для значений **`type`** в **`emit` / `on`** (например `WORKOUT_COMPLETED` со строкой `'workout:completed'` или другое согласованное именование **внутри префикса приложения** — главное, чтобы все имена проходили через этот модуль).
- Префикс **`app:`** добавляется только внутри класса к имени DOM-события; в списке хранятся **суффиксы** после `app:` (то, что передаётся в `emit('…', …)`).

### 3.4. Роли слоёв

| Слой | Действие |
|------|----------|
| Модуль | `eventBus.emit(EVENT_WORKOUT_COMPLETED, payload)` — без `react-router`. |
| Страница / layout | В **`useEffect`**: `const off = eventBus.on(EVENT_…, handler); return off;` — в обработчике `navigate` и т.д. **Без** отдельных хуков из `src/utils/eventBus`. |

### 3.5. Подписки и утечки

- Отписка — **всегда** вызовом функции, возвращённой из **`on`**; в React это **cleanup** эффекта.
- Глобальная шина на `window` не освобождает от снятия слушателей при размонтировании компонента.

### 3.6. Тестирование

- Юнит-тесты в среде с **`window`** (например **jsdom** в Vitest): подписка, **emit**, отписка, несколько слушателей на один `type`.
- Явного **`clear()`** на классе может не быть: изоляция тестов — через **вызов возвращённой отписки** в `afterEach` для зарегистрированных в тесте слушателей.

## 4. Этапы работ

1. **Контракт и код:** единый список имён, при необходимости `EventMap`, класс **`EventBus`** как выше, **`eventBus`**, баррель `src/utils/eventBus/index.ts`.
2. **Пилот:** эмит из модуля → в странице **`useEffect` + eventBus.on** → навигация; прямой роутинг из модуля убрать в этом сценарии.
3. **Документация:** краткое правило у барреля — кто эмитит, кто подписывается, что хуков в пакете шины нет.
4. **Проверка:** `npm run lint`, `npm run build`, `npm test`.

## 5. Критерии готовности

- Один **`eventBus`**; транспорт — **`CustomEvent` на `window`** с префиксом **`app:`** для фактического имени DOM-события.
- **`emit` / `on`** безопасны при отсутствии **`window`**.
- Имена логических типов — только из **единого списка** констант.
- Подписки в React снимаются через отписку из **`on`** в cleanup эффекта; **нет** хуков шины в `src/utils/eventBus`.
- Публичный импорт шины — через баррель; **`export *`** не использовать.
- Тесты покрывают поведение шины в доступной среде.

## 6. Риски

- **Двойная навигация** при забытых отписках — дисциплина **`useEffect`** cleanup.
- События видны **любому** коду на странице, слушающему `window` — для внутреннего приложения обычно приемлемо; при необходимости позже усилить контракт (не входит в текущую фичу).
- Порядок вызова нескольких слушателей одного типа задаётся поведением DOM; не полагаться на него в бизнес-логике без явной документации.
