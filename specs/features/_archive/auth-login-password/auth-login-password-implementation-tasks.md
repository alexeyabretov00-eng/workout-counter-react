# Задачи реализации: аутентификация (логин/пароль, API, SQLite)

Связанный план: [auth-login-password-plan.md](./auth-login-password-plan.md).

Используйте чекбоксы по мере выполнения.

---

## Этап A — Контракт API и каркас бэкенда

- [x] **A1.** Создать каталог сервера (например `server/`) и минимальный HTTP-сервер с health-check маршрутом.
- [x] **A2.** Подключить SQLite: файл БД вне git (путь через env или `.gitignore`), скрипт/код инициализации таблицы `users`.
- [x] **A3.** Зафиксировать контракт REST (markdown или OpenAPI): `POST /register`, `POST /login`, при необходимости `GET /me`, `POST /logout` — тела, коды ответов, формат ошибок.
- [x] **A4.** Обеспечить **один origin** для SPA и API: в dev — прокси в Vite (префикс API на бэкенд) или один процесс; **не** добавлять на API настройки CORS.

## Этап B — Логика API и безопасность

- [x] **B1.** Регистрация: валидация полей, уникальность логина, сохранение только хеша пароля.
- [x] **B2.** Вход: проверка пароля, выдача JWT или session cookie (как согласовано в плане); единый способ передачи на защищённых маршрутах.
- [x] **B3.** Middleware авторизации и хотя бы один защищённый эндпоинт для ручной/авто проверки.

## Этап C — Фронтенд

- [x] **C1.** Модуль клиента запросов к API по **тому же хосту**, что и приложение (относительные пути вроде `/api` или опциональный env-префикс пути **без** другого origin).
- [x] **C2.** Маршруты страниц входа и регистрации; интеграция в существующий `createBrowserRouter`.
- [x] **C3.** Компоненты форм (`src/components/…`, стили в `.styled.tsx`): поля логин/пароль, submit, состояния loading/error.
- [x] **C4.** Контекст или логика сессии (`src/contexts` / `src/logic` по соглашениям проекта): сохранение токена/сессии после входа, выход, проброс для клиента API.

## Этап D — Документация и проверка

- [x] **D1.** Обновить `README.md` и/или `docs/`: как запустить API и фронт при **одном origin** (прокси/единый сервер), переменные окружения, расположение файла SQLite.
- [x] **D2.** Ручная проверка: успешная регистрация и вход, отказ при дубликате логина, отказ при неверном пароле, защищённый эндпоинт с/без авторизации.
- [x] **D3.** Прогнать `npm run lint` и тесты проекта; при добавлении тестов для API — включить их в скрипты или CI по решению команды.

## Этап E — Локальный Docker (API + БД, один порт с SPA)

- [x] **E1.** `Dockerfile` (или отдельный `server/Dockerfile` / build target) для образа API: Node, запуск процесса из `server/`, переменные для пути к SQLite.
- [x] **E2.** Расширить `docker-compose.yml`: сервис `api` (без публикации порта на хост или только для отладки по согласованию), **volume** для файла БД, общая сеть с `web`.
- [x] **E3.** Доработать `docker/nginx/default.conf`: проксирование префикса API на upstream `api` (согласовать с маршрутами бэкенда и префикс `/api`).
- [x] **E4.** Убедиться, что собранный фронт в образе `web` обращается к API по относительным путям (без другого host:port в билде).
- [x] **E5.** Документация: `docker compose build` / `up`, порт, том с SQLite, отличие от прежней схемы «только статика».
- [x] **E6.** Ручная проверка через опубликованный порт `web`: регистрация и вход в UI, данные на томе переживают `docker compose down` (без удаления volume).

---

## Приоритизация

1. **A1–A4** — без контракта и работающего API фронт не стабилен.
2. **B1–B3** — полный цикл учётки на сервере.
3. **C1–C4** — UI и интеграция.
4. **D1–D3** — воспроизводимость и регрессия без Docker.
5. **E1–E6** — после стабильного API и клиента: compose, nginx, том, проверка в контейнерах.
