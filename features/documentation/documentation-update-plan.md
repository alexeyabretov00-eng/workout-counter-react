# План обновления документации

## 1. Контекст и проблема

- Основной источник правды для разработчиков и пользователей сейчас — [README.md](../../README.md).
- Реализация в коде опережает README: есть голосовое управление (Web Speech API), настраиваемый таймер отдыха, озвучка повторений на русском, отрисовка отсчёта отдыха на canvas.
- В [package.json](../../package.json) есть скрипт `preview`, который в README не описан.
- Дорожная карта в [todo.md](../../todo.md) не связана с публичной документацией — новым участникам неочевидно, что уже сделано и что в планах.

Цель обновления: документация должна совпадать с текущим поведением приложения, снижать порог входа и фиксировать договорённости для контрибьюторов.

## 2. Целевая аудитория

| Аудитория | Что нужно |
|-----------|-----------|
| Пользователь | как запустить, камера, браузер, голосовые команды, ограничения |
| Новый разработчик | стек, скрипты, структура `src/`, как запустить тесты и линтер |
| Контрибьютор | как добавить упражнение, где пороги и типы, как покрыть тестами |

## 3. Принципы

- **Один вход в репозиторий**: README остаётся точкой входа; при росте объёма — вынести детали в `docs/` с короткими ссылками из README.
- **Проверяемость**: каждый заявленный в документации сценарий (скрипт, команда) должен соответствовать `package.json` и фактическому UI.
- **Язык**: основной язык проектной документации — русский (как в текущем README и UI); при необходимости позже добавить краткий `README.en.md`.

## 4. Этапы работ

### Этап A. Аудит и инвентаризация

- Пройти пользовательский сценарий: `dev`, выбор упражнения, камера, голос, пауза, сброс, отдых, остановка камеры.
- Сверить список npm-скриптов и зависимостей с текстом README.
- Зафиксировать минимальные требования: современный Chromium-based браузер (Speech Recognition / камера), HTTPS или localhost для getUserMedia.

### Этап B. README: актуализация «что умеет»

- Добавить блок про голосовое управление: статусы, перечень команд (синхронизировать с константами в `App.tsx`), оговорка про поддержку браузера и разрешения микрофона.
- Описать таймер отдыха: UI (кнопки минут), поведение после сета, отображение на canvas.
- Упомянуть озвучку счёта повторений (если остаётся частью продукта).
- В «Скрипты» добавить `npm run preview` и кратко — для чего.

### Этап C. README: разработка и архитектура

- Обновить дерево модулей: явно указать `src/app/useWorkoutSession.ts` как ядро сессии (камера, MediaPipe, детектор, рендер).
- Кратко описать поток данных: кадр камеры → landmarker → детектор → состояние → canvas.
- Уточнить раздел «Как добавить упражнение»: сослаться на `ExerciseDetector`, `registry.ts`, пример тестов в `src/exercises/__tests__/`.

### Этап D. Дополнительные документы (по необходимости)

- `docs/voice-commands.md` — полный справочник команд и синонимов (чтобы не раздувать README).
- `docs/browser-requirements.md` — камера, микрофон, модели MediaPipe, типичные ошибки.
- Связать [todo.md](../../todo.md) с README одной фразой вроде «идеи и бэклог — в todo.md», без дублирования всего списка.

### Этап E. Качество и поддержка

- После правок: прогнать `npm run lint` и `npm run test`; при необходимости добавить в README примечание «перед PR».
- Договориться о правиле: значимые изменения в UX/командах сопровождать правкой документации в том же PR.

## 5. Критерии готовности

- README не содержит устаревших утверждений о возможностях приложения.
- Все скрипты из `package.json`, упомянутые в README, описаны корректно.
- Новый разработчик по README может запустить проект, понять слои и добавить тестируемый детектор.
- Пользователь находит описание голосовых команд и ограничений браузера (в README или в связанном файле `docs/`).
