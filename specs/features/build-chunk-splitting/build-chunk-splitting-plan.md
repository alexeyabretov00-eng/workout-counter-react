# План: разделение сборки на chunks (Vite + React Router)

Связанный чеклист: [build-chunk-splitting-implementation-tasks.md](./build-chunk-splitting-implementation-tasks.md).

## 1. Контекст и проблема

- Сборка выполняется через Vite (`npm run build`); конфигурация по умолчанию не задаёт явное разбиение vendor-чанков.
- Маршруты страниц собираются в `src/routes/routes.ts` через `import.meta.glob('../pages/*/index.tsx', { eager: true })`, поэтому **все** модули страниц и их зависимости попадают в **начальный** граф загрузки, даже если пользователь не открывает соответствующие пути.
- Тяжёлая зависимость `@mediapipe/tasks-vision` подключается из `PoseLandmarkerService` и тянется в бандл вместе с цепочкой импортов (например, через `useWorkoutSession`), что увеличивает объём JS до первого полезного кадра на главном сценарии.

Цель: уменьшить объём **начального** JS и при необходимости выделить предсказуемые чанки (страницы, крупные библиотеки), сохранив текущее поведение приложения и навигации.

## 2. Границы фичи

Входит:

- Стратегия **route-level** code splitting: ленивая загрузка компонентов страниц (или эквивалент через `React.lazy` / динамический `import()`), отказ от `eager: true` для регистрации страниц либо замена на паттерн, дающий отдельные чанки на маршрут.
- Настройка **Rollup/Vite** (`build.rollupOptions.output.manualChunks` и при необходимости `chunkFileNames`) для стабильных имён и разумного разделения vendor (например `react`/`react-dom`, `react-router`, `styled-components`, отдельный чанк под `@mediapipe/tasks-vision` при сохранении корректного порядка загрузки).
- Обработка **загрузки** на уровне UI: `Suspense` (и осмысленный fallback), отсутствие «белого экрана» без индикации при медленной сети.
- По возможности — **отложенный** импорт MediaPipe/сервиса позы только в момент, когда он реально нужен (инициализация тренировки/камеры), без дублирования логики детекции.

Не входит:

- Полный переход на SSR или другой бандлер.
- Оптимизация WASM/моделей MediaPipe на CDN (кроме косвенного эффекта от выноса JS-обёртки в отдельный chunk).
- Изменение продуктовой логики счётчика/упражнений, кроме минимальных точек под dynamic import.

## 3. Принципы

- **Измерять:** до и после — `vite build` и анализ отчёта (например `rollup-plugin-visualizer` или встроенный анализ размеров в логах Vite), зафиксировать размеры основных чанков.
- **Минимальный риск:** сначала маршрутный lazy load и Suspense, затем тонкая настройка `manualChunks`, затем отложенный импорт MediaPipe при отдельной проверке.
- **Сохранить контракт:** `navItems` и список маршрутов должны остаться корректными; публичные пути и редиректы — без регрессий.
- **Соглашения проекта:** импорты из баррелей `src`, отдельная ветка `feature/build-chunk-splitting`, три коммита цикла фичи (план → реализация → архив).

## 4. Техническое направление

### 4.1. Маршруты и страницы

- Убрать необходимость **eager** загрузки всех `pages/*/index.tsx`.
- Варианты (выбрать один согласованный в реализации):
  - экспорт из `index.tsx` **фабрики** маршрутов с `lazy(() => import('./Page'))` и `element` через `<Suspense>` на уровне layout или роут-обёртки;
  - или централизованный реестр с `lazy` на компоненты страниц, а метаданные `handle.nav` остаются в статическом объекте.
- Сохранить автоматическое обнаружение страниц по файловой структуре, если это возможно без возврата к полному eager-бандлу.

### 4.2. Vite `manualChunks`

- Выделить крупные зависимости в именованные чанки, избегая циклических зависимостей и дублирования модулей.
- Проверить совместимость с динамическими импортами страниц (чтобы страница не тащила лишний vendor, уже вынесенный в общий chunk).

### 4.3. MediaPipe

- Рассмотреть `import()` внутри `PoseLandmarkerService.init()` (или тонкий адаптер), чтобы пакет `@mediapipe/tasks-vision` не входил в стартовый chunk до вызова инициализации.
- Убедиться, что типы и ошибки загрузки обрабатываются так же, как сейчас (fallback lite-модели и т.д.).

## 5. Критерии готовности

- `npm run build` проходит без ошибок; в `dist/assets` видны отдельные чанки для страниц (или эквивалентный эффект в отчёте сборки).
- Начальный chunk (entry) **меньше**, чем до изменений, на репрезентативной сборке; тяжёлые зависимости не обязаны грузиться до перехода на нужный маршрут / до старта сценария с камерой — в зависимости от принятой стратегии.
- Ручная проверка: главная, админка (если есть), навигация, сценарий с камерой/позой — без регрессий.
- В чеклисте отмечены пункты верификации; при необходимости кратко задокументировано в `README.md` или `docs/`, как смотреть размеры бандла.

## 6. Риски

- **Неправильный `manualChunks`** — дубли модулей или слишком крупные чанки. Мера: итерации с визуализацией графа и просмотром `vite build --debug`.
- **Flash пустого layout** при lazy routes. Мера: единый `Suspense` + fallback в `AppPageLayout` или на уровне роутера.
- **Динамический import MediaPipe** — усложнение стека ошибок. Мера: сохранить существующие ветки `try/catch` инициализации, добавить понятный лог при сбое загрузки модуля.
