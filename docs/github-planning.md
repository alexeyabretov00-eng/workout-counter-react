# Планирование на GitHub: Milestone, Issues и Wiki

Этот документ дополняет раздел «Планирование фич и исправлений» в `README.md`: в репозитории по-прежнему создаются каталоги `specs/features/…`, `specs/fixes/…` или `specs/refactor/…` с планом и чеклистом. Для задач этого цикла GitHub-трекинг обязателен: **этап 1** — создание Milestone и Issues, **этап 3** — закрытие связанных Issues и Milestone. При желании можно хранить развёрнутое ТЗ в **Wiki**.

## Роли артефактов

| Артефакт | Назначение |
|----------|------------|
| Каталог в `specs/…` | Источник правды в git: план, чеклист, история в PR |
| **Milestone** | Эпик одной задачи: заголовок, прогресс по закрытию issues, дедлайн по желанию |
| **Issues** | Конкретные работы; в PR указывайте `Fixes #N` / `Closes #N` |
| **Wiki** (опционально) | Длинное ТЗ, схемы, ссылки на макеты; в описании Milestone — ссылка на wiki-страницу |

Рекомендуемая формулировка в описании Milestone: краткая цель и фраза вроде: «Детали — в Wiki и связанных issues» (если Wiki используете) плюс ссылки на файлы плана в ветке или на `main` после merge (пути от корня в обратных кавычках или URL `blob` — см. `docs/markdown-paths.md`).

## Декомпозиция Issues (пример порядка)

Для нетривиальной фичи удобно завести несколько issues в одном milestone (порядок в заголовках или в тексте):

1. **[План]** — сводка, ссылки на `specs/…`, критерии готовности эпика.
2. **Контракт / API / данные** — форматы, клиент, моки.
3. **Домен и состояние** — оркестрация модуля, хранилище, контексты (в терминах этого проекта: `HomeModule.tsx`, `store`, `contexts` и т.д.).
4. **UI** — компоненты, состояния загрузки/ошибка/пусто.
5. **Маршруты / страницы** — если затронуто.
6. **Тесты, сборка, документация** — по необходимости.

Для маленького исправления достаточно одного Issue в одном Milestone.

## Привязка к этапам цикла

1. **Этап 1 (план):**
   - создать Milestone;
   - создать и привязать к нему Issues.
2. **Этап 2 (реализация):**
   - вести работу и при необходимости ссылаться в PR на `Closes #N`.
3. **Этап 3 (архивирование):**
   - закрыть связанные Issues (если не закрылись автоматически через merge PR);
   - закрыть Milestone.

## Шаблоны Issues в репозитории

В каталоге `.github/ISSUE_TEMPLATE/` лежат формы для создания issue: фича, исправление, рефакторинг, эпик плана. После push ветки в GitHub при **New issue** можно выбрать шаблон.

## GitHub CLI (`gh`)

Установите [GitHub CLI](https://cli.github.com/) и выполните `gh auth login`. Подставьте `OWNER`, `REPO` и нужную ветку в ссылках на файлы.

### Создать Milestone

```bash
gh api repos/OWNER/REPO/milestones -f title="Фича: краткое название" -f description="План работ по …. Детали — в Wiki (ссылка) и в specs/features/имя/. Связанные issues ниже."
```

Запомните номер milestone из ответа JSON (`number`) или найдите title в UI.

### Создать Issue и привязать к Milestone

Вариант с именем milestone:

```bash
gh issue create --repo OWNER/REPO --title "[План] Краткое название" --body "Сводка и ссылки на specs/…" --milestone "Фича: краткое название"
```

Вариант с номером milestone через API (если нужен точный JSON):

```bash
gh api repos/OWNER/REPO/issues -f title="API: …" -f body="…" -f milestone=1
```

Повторите `gh issue create` для каждой подзадачи с тем же `--milestone`.

### Закрыть Issues и Milestone (этап 3)

Закрыть issue:

```bash
gh issue close 123 --repo OWNER/REPO --comment "Завершено в рамках этапа 3 (архивирование)."
```

Закрыть milestone через API:

```bash
gh api repos/OWNER/REPO/milestones/MILESTONE_NUMBER -X PATCH -f state=closed
```

### PowerShell (многострочный body)

В PowerShell удобнее передать тело из файла:

```powershell
Set-Content -Path body.md -Value "Строка1`nСтрока2" -Encoding utf8
gh issue create --repo OWNER/REPO --title "UI: …" --body-file body.md --milestone "Фича: краткое название"
```

## Просьба к агенту (Cursor)

Для задач по циклу со спеком агент обязан вести GitHub-артефакты по этапам (создание на этапе 1, закрытие на этапе 3). Если нет отдельного разрешения на выполнение `gh`, агент должен выдать готовые команды.
