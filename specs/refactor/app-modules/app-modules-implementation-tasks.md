# Задачи реализации: выделение модулей (`*Module`)

Связанный план: [app-modules-plan.md](./app-modules-plan.md).

Используйте чекбоксы по мере выполнения.

---

## Этап A — Соглашение зафиксировано

- [ ] **A1.** Утвердить корневой каталог модулей: `src/modules/<ИмяModule>/` (PascalCase, суффикс `Module`).
- [ ] **A2.** Утвердить правило: снаружи модуля импорты только из публичного API; предпочтительная форма в коде — **`@modules/<ИмяModule>`** (см. план).
- [ ] **A3.** Утвердить допустимую внутреннюю структуру (подпапки, внутренние баррели) и границу с `src/components` / `pages/*/components` / `pages/HomePage/*` (см. план): компоненты в **`pages/<Page>/components`** — **только** для объединения модулей на странице; исключение **`HomePage`** — по `docs/src-layout.md`.
- [ ] **A4.** При вводе алиаса в репозитории: добавить в **`tsconfig.app.json`** и **`vite.config.ts`** сопоставление **`@modules/*` → `src/modules/*`**, обновить таблицу в **`docs/import-aliases.md`** (строка для `@modules` и пример импорта).

## Этап B — Первый эталон в коде (по готовности продукта)

- [ ] **B1.** Выбрать первую область для модуля (например учётная запись: вход и регистрация на `LoginPage` и `RegisterPage`) или отложить до появления стабильной границы.
- [ ] **B2.** Создать `src/modules/<ИмяModule>/` с публичным `index.ts` и перенести/собрать артефакты без смены поведения.
- [ ] **B3.** Подключить страницы через публичное API модуля (`@modules/<ИмяModule>` после настройки алиаса); убрать глубокие импорты из модуля снаружи.
- [ ] **B4.** При вложенности: зависимость между модулями только через баррели; задокументировать или устранить риск циклов.

## Этап C — Документация и проверка

- [ ] **C1.** Кратко описать модули в `README.md` и/или `docs/` (одна страница или раздел — по решению команды), со ссылкой на этот план.
- [ ] **C2.** При необходимости добавить правило в `.cursor/rules/` (импорты модулей, суффикс `Module`) согласованно с `docs/import-aliases.md`.
- [ ] **C3.** `npm run lint`, `npm test`, `npm run build`; ручная проверка сценариев затронутых страниц.

---

## Приоритизация

1. **A1–A4** — без них миграции в коде будут непоследовательны; **A4** выполняется вместе с первым использованием `@modules/…` в коде.
2. **B1–B4** — когда есть реальный кандидат; можно выполнять не в одной задаче.
3. **C1–C3** — после появления эталона или вместе с ним.
