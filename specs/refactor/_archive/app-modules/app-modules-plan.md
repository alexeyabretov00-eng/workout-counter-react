# План: выделение модулей приложения (`*Module`)

## 1. Контекст

Сейчас границы переиспользования заданы частично: общие UI-примитивы — в `src/components`, сложная оркестрация экрана тренировки — в `src/pages/HomePage/` (`logic`, `contexts`, `selectors`, `containers`, `components`). Для **сквозных доменных областей** (например аутентификация и регистрация, используемые на разных страницах) полезна единая точка: **модуль** — переиспользуемая часть приложения со своими артефактами и явным публичным API.

## 2. Цели

- Зафиксировать определение **модуля**: переиспользуемый срез приложения; внутри модуля хранятся **все артефакты**, нужные для его работы (UI, хуки, контексты, клиент API, типы, тесты, stories — по необходимости).
- Зафиксировать **использование на странице**: на одной странице может быть **один** модуль или **несколько**; модули **могут подключаться друг в друга** только через публичное API.
- Зафиксировать роль **`src/pages/<Page>/components`**: там **могут** быть компоненты **только** для **объединения (компоновки) модулей** на странице — порядок, обёртка, разметка без выноса доменной логики из модулей.
- Зафиксировать **именование**: корневая сущность модуля и корневая папка в `src/modules` содержат суффикс **`Module`** (например `LoginModule`, `RegistrationModule`).
- Привести в соответствие с существующими правилами: баррели `index.ts` с явными реэкспортами, **без** `export *`; импорты между верхнеуровневыми областями `src` — из баррелей (см. `docs/import-aliases.md`).
- Зафиксировать **алиас каталога модулей**: в `tsconfig.app.json` и `vite.config.ts` — сопоставление шаблона **`@modules/*`** с **`src/modules/*`** (аналогично тому, как для других корней описано в `docs/import-aliases.md`). **Импорты снаружи** оформляются как **`@modules/<ИмяModule>`** (префикс **`@modules`**, имя модуля — как у папки), например: `import { LoginModule } from '@modules/LoginModule'` — разрешается в `src/modules/LoginModule/index.ts`.

## 3. Не цели (в рамках этого плана)

- Обязательная миграция всего кода сразу: внедрение — **по мере задач**, когда граница «модуль / страница / общий компонент» очевидна.
- Изменение наблюдаемого поведения продукта: перенос кода в модуль — **рефакторинг** при сохранении поведения.

## 4. Определения

| Термин | Смысл |
|--------|--------|
| **Модуль** | Переиспользуемая часть приложения с **одной ответственностью** на уровне продукта (доменный срез). Всё необходимое для работы модуля — **внутри** корневой папки модуля (или явно описанные зависимости на другие модули/API). |
| **Корень модуля** | Каталог `src/modules/<ИмяModule>/`, где `<ИмяModule>` — PascalCase и оканчивается на `Module`. |
| **Публичное API модуля** | Экспорты из `src/modules/<ИмяModule>/index.ts` (и при необходимости узкие под-баррели **внутри** модуля). Снаружи модуля импорт **только** из этого API, не из глубоких путей; предпочтительная форма — **`@modules/<ИмяModule>`** (алиас `@modules/*` → `src/modules/*`). |
| **Страница** | `src/pages/<PageName>/` — композиция и маршрутизация: подключает один или несколько модулей, не дублирует доменную логику модуля. Локальные компоненты страницы (`pages/.../components`) — **только** для **склейки** модулей на экране (см. §5–7). |

**Пример (иллюстрация границы):** модули **`LoginModule`** и **`RegistrationModule`** — формы/хуки/вызовы API входа и регистрации; страницы `LoginPage` и `RegisterPage` только размещают соответствующие входные точки модулей (и общую оболочку страницы).

## 5. Границы слоёв

- **`src/components`**: нейтральные примитивы и виджеты без доменной логики приложения — как сейчас (`docs/components.md`). Модуль **может** импортировать из барреля `src/components`.
- **`src/pages/<Page>/components`** (в модульной схеме): компоненты **допустимы только** для **объединения модулей** на странице — раскладка, порядок, лёгкая оболочка **без** доменной логики, которая должна жить в **`@modules/…`**. Если блок нужен на **нескольких** страницах или тянет домен — **модуль** или `src/components` по смыслу, а не раздувание `pages/.../components`.
- **`src/pages/HomePage/…`**: **исключение** — действует отдельное соглашение для экрана тренировки (`docs/src-layout.md`, `.cursor/rules/src-layout.mdc`): там свои слои (`logic`, `contexts`, `containers`, `components` и т.д.), это **не** сводится к правилу «только склейка модулей»; появление **`src/modules`** для других областей приложения это соглашение **не отменяет**.

**Зависимости между модулями:** модуль A импортирует модуль B только из публичного API B — в коде это **`@modules/<BModule>`** (эквивалентно `src/modules/<BModule>/index.ts`). Циклические зависимости между модулями избегать; при риске цикла — вынести общий контракт в `src/types` / небольшой общий пакет по согласованию команды.

## 6. Рекомендуемая внутренняя структура модуля

Не жёсткий стандарт на все случаи — ориентир:

- `src/modules/<ИмяModule>/` — снаружи импорт **`@modules/<ИмяModule>`** (см. цели про алиас `@modules/*`).
  - `index.ts` — публичное API.
  - По необходимости подпапки (каждая с `index.ts` при публичности внутри модуля): `components/`, `hooks/`, `contexts/`, `api/` или `services/`, `types/`, `__tests__/`, `__stories__/` и т.д.
- Корневой **компонент-вход** (если есть один основной для страницы) по соглашению проекта: именованный `const`, стили в `.styled.tsx`, тема из `src/theme`.

Имена **публичных** компонентов/хуков модуля не обязаны повторять суффикс `Module` в каждом идентификаторе; суффикс обязателен для **имени модуля как единицы композиции** (папка + при необходимости корневой тип/namespace в документации).

## 7. Страницы и композиция

- **Компоненты в `pages/<Page>/components`:** по смыслу этого плана — **только** чтобы **объединить** на странице один или несколько импортов из **`@modules/…`** (и при необходимости общие **`@components`**). Не место для дублирования бизнес-логики модулей.
- Одна страница **=** один модуль: страница рендерит, например, входную точку из `@modules/…` или единый провайдер + дочерний маршрут — как договорит команда в задаче.
- Одна страница **=** несколько модулей: допустимо, если ответственность разделена (например модуль «шапка сессии» + модуль «форма входа»); склейка — в компоненте страницы или в `pages/.../components`.
- **Модуль внутри модуля:** реализуется импортом публичного API другого модуля, без прямого доступа к внутренним файлам.
- **`HomePage`:** не подпадает под узкое правило пункта выше — см. §5 и `docs/src-layout.md`.

## 8. Как убедиться в отсутствии регрессии

- Сборка и тесты: `npm run build`, `npm test`, `npm run lint`.
- Ручная проверка затронутых маршрутов и сценариев (для учётки — вход, регистрация, ошибки валидации).

## 9. Критерии готовности цикла рефакторинга

- В репозитории есть согласованное описание модулей (этот план + закрытый чеклист в `app-modules-implementation-tasks.md`).
- При появлении первого модуля в коде: существует `src/modules/<ИмяModule>/` с баррелем `index.ts`, страницы и другие модули подключают его через **`@modules/<ИмяModule>`** (алиас `@modules/*` настроен в `tsconfig.app.json` и `vite.config.ts`).
- При необходимости кратко обновлены `README.md` и/или `docs/` (ссылка на модульную границу), без противоречий с `docs/src-layout.md` и `docs/components.md`.
