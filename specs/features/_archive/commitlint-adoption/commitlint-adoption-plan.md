# План внедрения commitlint

Связанный чеклист: [commitlint-adoption-implementation-tasks.md](./commitlint-adoption-implementation-tasks.md).

## 1. Контекст и проблема

- История коммитов в командной работе со временем становится неоднородной по формату и смысловой структуре.
- Без автоматической проверки сообщение коммита может быть нечитаемым, не соответствовать договорённостям и затруднять ревью/релизные заметки.
- Требуется стандартизировать формат commit messages и встроить проверку в локальный workflow.

Цель: внедрить `commitlint` с понятными правилами и автоматической проверкой перед созданием коммита, чтобы улучшить качество истории репозитория.

## 2. Границы фичи

Входит:

- Подключение `commitlint` и базового conventional-конфига.
- Настройка конфигурационного файла проекта.
- Подключение проверки в git hooks (через существующий подход проекта к хукам).
- Документация формата коммитов и примеров для команды.
- Проверка работоспособности на валидных и невалидных сообщениях.

Не входит:

- Массовое переименование/переписывание старой истории коммитов.
- Изменение git-flow, политики ветвления и процесса релизов.
- Внедрение дополнительных линтеров коммитов/PR beyond scope текущей фичи.

## 3. Принципы внедрения

- **Минимальный порог входа:** правила должны быть понятны и применимы в повседневной работе.
- **Единый стандарт:** использовать conventional commits как базу без избыточной кастомизации на старте.
- **Автоматическая проверка:** разработчик получает обратную связь до попадания коммита в репозиторий.
- **Прозрачная документация:** примеры корректных и некорректных сообщений доступны в README или docs.
- **Пошаговая интеграция:** сначала инфраструктура, затем хуки, затем документация и проверка.

## 4. Целевая конфигурация

- `commitlint.config.*` в корне репозитория с расширением conventional-конфига.
- Git hook на `commit-msg`, который запускает `commitlint` для введённого сообщения.
- При необходимости npm-скрипт для ручной проверки сообщений (для локальной отладки/CI-сценариев).
- Краткий раздел в документации:
  - формат: `type(scope): subject`;
  - допустимые `type`;
  - короткие примеры.

## 5. Этапы работ

### Этап A. Подготовка зависимостей

- Добавить пакеты `@commitlint/cli` и `@commitlint/config-conventional` (exact-версии).
- После изменения зависимостей выполнить чистую переустановку (`node_modules` + `package-lock.json` -> `npm install`).
- Убедиться, что установка проходит без конфликтов.

### Этап B. Базовая настройка commitlint

- Добавить конфиг `commitlint` с conventional-правилами.
- Зафиксировать минимальные локальные правила (например, ограничение длины header при необходимости).
- Проверить запуск `commitlint` вручную на тестовых сообщениях.

### Этап C. Интеграция с git hooks

- Подключить проверку `commit-msg` через используемый в проекте механизм хуков.
- Убедиться, что невалидный коммит блокируется, а валидный проходит.
- Сохранить совместимость с текущими pre-commit/другими хуками (если уже есть).

### Этап D. Документация и принятие

- Обновить `README.md` (или `docs/`) с краткой памяткой по commit messages.
- Добавить 5-7 типовых примеров под текущие задачи проекта (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`).
- Провести финальную проверку локального workflow и зафиксировать результат.

## 6. Риски и меры снижения

- Риск излишне строгих правил, мешающих коммитить.  
  Мера: старт с базового conventional-конфига и минимального числа custom-ограничений.
- Риск несовместимости с текущими хуками.  
  Мера: подключать и проверять `commit-msg` отдельно, без изменения существующих pre-commit сценариев.
- Риск непонимания формата командой.  
  Мера: короткая памятка и примеры в документации рядом с командами запуска.

## 7. Критерии готовности

- В проекте есть рабочий конфиг `commitlint` с agreed baseline rules.
- `commit-msg` hook запускает проверку автоматически.
- Невалидные сообщения коммита блокируются, валидные проходят.
- Документация описывает формат и даёт практичные примеры.
- Локальная проверка интеграции выполнена и подтверждена.
