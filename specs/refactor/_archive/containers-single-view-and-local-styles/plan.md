# План: один контейнер — один презентационный компонент и стили рядом с ним

## 1. Контекст

Сейчас контейнеры слотов (`src/containers/*`) по смыслу соответствуют правилу «один публичный компонент — одна папка», но **разметка и оформление** размазаны:

- **`ExerciseControlBarContainer`** и **`StatusBarContainer`** возвращают **фрагмент** (`<>`) с **несколькими** корневыми узлами (селекты, кнопки, `span`). Контейнер одновременно и подключает данные, и описывает состав UI.
- **`StageContainer`** уже имеет **один** корневой узел (`div.stage-container`), но связанные с ним классы (лоадер, пауза, canvas) описаны не рядом с контейнером, а в **`src/App.css`** вместе со стилями других слотов.
- Стили слотов **`.controls`**, **`.status-bar`**, **`.stage`**, бейджи состояний (`.model-state`, `.camera-state`, `.voice-state`, …) и блок сцены (`.stage-camera-loader`, …) сосредоточены в **`App.css`**, хотя по соглашению для UI-виджетов стили должны жить **рядом с компонентом** (см. `docs/components.md`, `.cursor/rules/components.mdc`).

Цель рефакторинга — выровнять структуру с этим соглашением **без изменения** наблюдаемого поведения и внешнего вида для пользователя.

## 2. Цели

1. **Один контейнер — один дочерний презентационный компонент:** каждый контейнер после рефакторинга рендерит **ровно один** корневой узел вида `<ИмяВью {...} />`, куда через пропсы передаётся всё, что приходит из `use…ContainerSelector` (и при необходимости стабильные коллбеки). Сборка разметки из нескольких `Button` / `Select` / `span` переносится в **`src/components`**.
2. **Стили рядом с презентацией:** правила, относящиеся к конкретному слоту (панель управления, статус-бар, сцена), переносятся из `App.css` в **`<Имя>.css`** в папке соответствующего компонента в `src/components`, с импортом из `<Имя>.tsx`.
3. **`App.css`** остаётся местом для **глобальных** или **остаточных** правил (например `* { box-sizing: border-box; }`, оформление заголовка в слоте `header`, если он по-прежнему задаётся инлайн в `App.tsx`), без дублирования правил перенесённых виджетов.

## 3. Предлагаемая структура

| Компонент (презентация) | Папка | Контейнер-обёртка | Примечание |
|-------------------------|--------|-------------------|------------|
| `ExerciseControlBar` | `src/components/ExerciseControlBar/` | `ExerciseControlBarContainer` | Пропсы: значения из селектора + `onExerciseChange`, `onStartPause`, `onReset`, `onShutdown`, `onRestDurationChange` (или один объект коллбеков — на усмотрение реализации, главное — без логики сессии внутри). |
| `WorkoutStatusBar` (или другое однозначное имя, например `SessionStatusBar`) | `src/components/WorkoutStatusBar/` | `StatusBarContainer` | Пропсы: строки/флаги для отображения, без `useContext`. |
| `Stage` (или `WorkoutStage`, если `Stage` кажется слишком общим) | `src/components/Stage/` | `StageContainer` | Пропсы: `canvasRef`, `isCameraInitializing`, `isPaused` — как сейчас даёт селектор. |

Каждая папка в `src/components`: `<Name>.tsx`, `<Name>.css`, `index.ts`, явный реэкспорт в `src/components/index.ts` (без `export *`).

Контейнеры **не** получают новых пропсов данных сессии снаружи; контракт «данные только через селектор» сохраняется (`docs/src-layout.md`).

## 4. Стили и классы

- Перенести в CSS презентационных компонентов блоки из `App.css`, которые относятся к:
  - панели управления (сейчас в том числе через секцию `.controls` — см. ниже);
  - статус-бару (`.status-bar`, `.model-state`, `.camera-state`, `.voice-state`, `.session-state`, `.camera-error`);
  - сцене (`.stage` как **обёртка области**, `.stage-container`, лоадер, пауза, canvas и `@keyframes` для спиннера).
- **BEM и явные классы:** по возможности корневой класс презентационного компонента не опирается на селекторы вида `.controls button`; классы вида `exercise-control-bar`, `workout-status-bar`, `stage` (с элементами/модификаторами по BEM) предпочтительнее для перенесённых правил.
- Секции **`AppLayout`** сейчас несут классы `header`, `controls`, `status-bar`, `stage`. Варианты (выбрать один и зафиксировать в реализации):
  - **A.** Оставить классы на `<section>` только для минимальной связи с раскладкой; перенести flex/gap для «полосы контролов» и статус-бара на **корень** презентационного компонента внутри слота (тогда часть правил уезжает из селектора `.app-layout__section.controls` в `ExerciseControlBar.css`).
  - **B.** Дополнить `AppLayout.css` правилами для модификаторов секций (`app-layout__section--controls` и т.д.), а специфику виджетов держать в локальных CSS компонентов.

Критерий: визуально и при типичных действиях (старт, пауза, смена упражнения, статусы) результат совпадает с текущим.

## 5. Этапы реализации (логический порядок)

1. Добавить **`Stage`** (или выбранное имя) в `src/components`, перенести разметку из `StageContainer` и соответствующие стили из `App.css`; контейнер оставить тонким слоем «селектор + `<Stage … />`».
2. Добавить **`WorkoutStatusBar`**, перенести разметку и стили статусов; обновить **`StatusBarContainer`**.
3. Добавить **`ExerciseControlBar`**, перенести разметку и стили панели; обновить **`ExerciseControlBarContainer`**.
4. Подчистить **`App.css`**, убедиться, что не осталось «висячих» правил для перенесённых блоков.
5. Обновить **`docs/src-layout.md`** (и при необходимости **`docs/components.md`**) одной-двумя фразами: у контейнера презентация — в отдельном компоненте `components`, стили — в соседнем `.css`.

Порядок этапов 1–3 можно слегка переставить, если удобнее сначала вынести самый простой слот.

## 6. Проверка отсутствия регрессии

- Ручная проверка: сетка `AppLayout`, отступы; панель управления (селекты, кнопки, disabled-состояния); строка статусов; сцена (лоадер камеры, canvas, пауза).
- `npm test` и `npm run build` без ошибок.

## 7. Критерии готовности

- Каждый из трёх контейнеров рендерит **один** дочерний презентационный компонент из `src/components`.
- Стили слотов, перечисленные в разделе 4, подключены из **`.css` рядом с компонентом**, а не из монолитного `App.css` (кроме явно глобальных/заголовка).
- Публичные баррели (`src/components/index.ts`, `src/containers/index.ts`) и импорты между папками `src` — по правилам (`imports-via-index.mdc`).

## 8. Вне скоупа

- Вынос заголовка из `App.tsx` в отдельный компонент (например `AppHeader`) — по желанию отдельным небольшим рефакторингом.
- Изменение контрактов контекстов/селекторов или поведения тренировки — не входит в эту задачу.
